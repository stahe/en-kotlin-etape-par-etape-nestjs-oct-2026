    8. The RdvMedecins server, a black box

    Examples 22 through 25, followed by the case study, interact with a server: the JSON server of the [RdvMedecins] application. This is the [NestJS] server for courses [React], [Vue.js], [Angular], and [Flutter]: the server for the [NestJS] course, whose controllers no longer generate HTML pages but instead produce JSON responses. Readers of these lectures are already familiar with this chapter, which is reproduced here almost unchanged; they can focus solely on the section on authentication, which explains what changes for a mobile application.

    In this course, this server is a black box: you don’t need to know how it’s written. All that matters is its API—that is, the list of HTTP requests it accepts and the responses it returns. This is the typical situation for a client developer: the API is a contract, and the server team can change whatever they want behind that contract. Its source code is provided ([rdvmedecins-nestjs-json] folder) and extensively commented, for the curious reader.

    This chapter explains how to install the server, describes its API, and queries it using [curl].

    8.1. The RdvMedecins Application

    The application manages appointments for a medical practice. It has three roles:

    Role
    Who
    What they can do
    [ADMIN]
    The administrator ([admin])
    Schedule and cancel appointments for all patients; manage doctors and clients
    [DOCTOR]
    Doctors ([pelissier], [tatou], [dupont])
    Schedule and cancel appointments for all patients; view all names in the calendars
    [USER]
    Patients ([martin], [durand], [bistrou], [german])
    book appointments for themselves; cancel their appointments; manage their accounts. In a calendar, they cannot see the names of other patients

    Demo accounts use their login as the password. The management rules are verified by the server, regardless of the client:

    • no appointments in the past;
    • only one upcoming appointment per patient;
    • a time slot can only be booked once per day;
    • two doctors (or two clients) cannot have the same first and last names; a login belongs to only one account;
    • a doctor with scheduled appointments cannot be deleted;
    • A record that has been modified in the meantime by someone else cannot be overwritten (optimistic lock);
    • A patient is never assigned the name of another patient.

    8.3. Response Format

    All URLs begin with [/api]. A successful request receives a 2xx status code and, in its body, the requested data in the format JSON. A rejected request receives a 4xx or 5xx status code and, in the body, TOUJOURS, which follows the same format:

    1
2
3
4
5
6
    {
  "statusCode": 400,
  "cle": "ERRORS.INVALID_FORM",
  "params": { "min": "6" },
  "champs": { "nom": "ERRORS.LASTNAME_REQUIRED", "password": "ERRORS.PASSWORD_TOO_SHORT" }
}
    • [statusCode]: the code HTTP, repeated in the body;
    • [cle]: the message translation key. The server never returns text to be displayed: it no longer knows the user’s language. It is the client that translates the key using its dictionaries (see Example 21);
    • [params] (optional): the message parameters ([Au moins {min} caractères], [Réessayez dans {minutes} minute(s)]);
    • [champs] (optional): for a rejected form, the error for each field.

    Codes used:

    8.4. Authentication

    The client authenticates using [POST /api/auth/login], with a username, password, and CAPTCHA response. In return, the server sends, in the [Set-Cookie] header of its response, a cookie containing a signed token JWT:

    1
    Set-Cookie: rdvmedecins_jwt=eyJhbGciOiJIUzI1NiIs...; Max-Age=7200; Path=/api; HttpOnly; SameSite=Strict

    The client must then present this cookie, in the [Cookie] header, with every request to [/api]: this is how the server knows who is making the request.

    This server was designed for web clients, and its design choices are driven by the risks specific to web browsers:

    • [HttpOnly]: The [JavaScript] code on the page cannot PAS read this cookie. A malicious script injected into the page would therefore be unable to steal the token. Consequence for the client: it cannot determine on its own whether it is logged in. It asks the server ([GET /api/auth/moi]);
    • [Path=/api]: The cookie is only included in requests to API;
    • [SameSite=Strict]: The browser attaches the cookie only to requests sent to a page on this site. A malicious page on another site cannot cause the browser to act on the user’s behalf (a so-called CSRF attack);
    • [Max-Age=7200]: It expires after two hours, at the same time the token expires.

    A second safeguard against CSRF attacks: the server rejects (415) any POST request whose body is not in JSON. A compromised HTML form on another site cannot send JSON.

    What about a mobile app? There is no browser: no one stores the cookie or sends it back on its own. The app will take on this role: the [OkHttp] library, which is entrusted with a “cookie jar” (a [CookieJar]), reads the [Set-Cookie] header from responses and writes the [Cookie] header in requests (Example 23). The attributes [HttpOnly] and [SameSite] apply only to browsers: they have no effect on it, just as they have no effect on [curl].

    A calendar entry ([GET /api/agenda]) describes a time slot (ET) and what the logged-in user is authorized to do with it:

    1
2
3
4
    { "id": 3, "hdebut": 8, "mdebut": 40, "hfin": 9, "mfin": 0,
  "libre": false,

    • [libre]: Is the time slot available on that day?

    The server handles DÉCIDE; the client displays it. And even if a client were to cheat (by displaying a “Book” button when it shouldn’t), the server would double-check everything at the time of booking.

    8.6. Query the API using curl

    The server directory [curl] contains the JSON bodies of the requests in this chapter, with one file per request. For example, [curl/login-admin.json]:

    1
    { "login": "admin", "password": "admin", "captchaId": "-", "captcha": "test" }

    Commands are entered in a console opened in the [rdvmedecins-nestjs-json] directory. Some options for [curl]:

    • [-i]: also display the response headers; [-s]: without a progress bar;
    • [--json @fichier]: send the contents of the file in POST, with the header [Content-Type: application/json] (curl 7.82 and later; with an older version, use [-H "Content-Type: application/json" -d @fichier]);
    • [-X PUT], [-X DELETE]: the HTTP method;
    • [-c cookies.txt]: save the received cookies to this file; [-b cookies.txt]: send them back. This is how [curl] “stays logged in” from one command to the next, just as a browser would.

    Under [PowerShell], you must enter [curl.exe] and not [curl] (which refers to another command there). The somewhat lengthy responses for JSON have been formatted for this document, and the headers for [Date], [ETag], [Connection], and [Keep-Alive] have been removed.
